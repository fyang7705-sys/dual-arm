# 视频失败诊断与最小修复（2026-11-07）

## 观察到的证据

本次用户视频与仓库中的
`third_party/RoboDojo/eval_result/.../2026-11-05_23-43-14/episode_0000000_cam_head_fail.mp4`
字节级 MD5 一致。对应 `_result.json` 记录 `success_rate: 0.0`、`score: 0.0`。
视频 22.04 秒、551 帧；头部相机画面可见三个积木始终留在桌面，双臂多次移动到积木旁边或明显空白桌面位置，没有完成夹取。

本仓库中对应 ACT 训练日志显示：

- 训练 200 epochs，训练 L1 最后约 0.0299，验证 L1 约 0.0376；
- KL 在第 1 epoch 为 0.2607，第 2 epoch 已降到 0.000748，后续日志四舍五入为 0.000000；
- 失败评测 manifest 确认加载的是 `policy_best.ckpt`、epoch 178、`eval_chunk_size=16`。

因此“训练 loss 下降”并未转化为可执行抓取。模型不是显式输出积木列表，而是输出未来连续动作块；视频中看似多个“抓取位置”的动作不能解释成检测到了五个物体。

## 高置信度根因

1. **视觉全局平均池化丢失精确空间布局。** ACT 和 DP 原实现均将卷积特征 `AdaptiveAvgPool2d(1)` 压成一个向量。相机里“有积木”可能被编码，但左/右、桌面上的具体位置被显著弱化。对于绝对末端位姿回归，这是结构性缺陷；不同积木布局会被压到相似视觉向量，策略容易输出折中/错误目标。
2. **ACT CVAE 后验塌缩。** 现有训练日志 KL 在第 2 epoch 后几乎为零，说明 latent 基本没有承载不同示范轨迹的模式信息。推理固定 `z=0`，遇到同类视觉状态对应不同动作阶段时，L1 训练容易得到平均动作。
3. **ACT 评测每次开环执行 16 步。** 这期间即使积木/夹爪/末端状态已偏离预期，也不会重新计算动作。对精细抓取而言太长，误差会累积。
4. **随机空间裁剪与绝对坐标动作标签不一致。** 原增强把图像随机裁切/缩放，但没有同步变换绝对 EE 动作标签，会人为改变积木像素位置而保持世界坐标标签不变。对定位任务可能引入标签噪声。

这些根因与视频中的“空抓、目标左右漂移”一致。由于本 ZIP 不含 HDF5 示范数据和训练 checkpoint，尚不能直接验证每个 episode 的相机帧—动作时间对齐，也不能在此处复现真实 Isaac 物理成功率。

## 已实施的最小代码改动

- ACT 新配置启用 `spatial_tokens: true`：4×4 图像 token 进入 Transformer decoder，并带可学习位置编码；不再只给 decoder 一个全局图像向量。旧 checkpoint 通过旧配置仍可走原结构。
- DP 新配置启用 `spatial_features: true`：保留 6×6 卷积空间网格后再投影，避免全局池化抹去目标位置。旧 checkpoint 通过旧配置仍可走原结构。
- ACT KL 权重改为 1.0，并用 20 epoch 线性 warmup，避免一开始强 KL 把 latent 压塌；训练日志继续记录原始 KL。
- ACT / DP 训练保留轻微亮度、对比度增强，但新配置关闭随机空间裁剪（`augment_spatial: false`），防止图像坐标与绝对 EE 标签错位。
- ACT / DP 评测服务器默认 `--chunk 1`，每个动作步重新读取图像和本体状态并规划，降低开环漂移。可通过 `ACT_EVAL_CHUNK` / `DP_EVAL_CHUNK` 环境变量显式覆盖，但建议先保持 1。
- 修正 DPPO 从离线 checkpoint 继承架构配置时遗漏 `spatial_features` 的问题；否则在线阶段保存的模型会错误地按旧全局池化架构重建。
- 增加空间编码回归测试：相同物体图案放在图像左侧和右侧时，编码输出必须不同。

## 训练与验收顺序

1. 先确认 `data/RoboDojo/stack_blocks/arx_x5/data/episode_*.hdf5` 是真实示范数据，不要用 `hold_demos` 或合成数据。
2. 用新配置重新训练 ACT 和 DP（新空间编码参数与旧 checkpoint 不兼容；不要加载旧模型继续训练）。
3. 先各跑 1 个 layout 的评测视频，检查第一次接近是否指向当前积木，夹爪是否在接触前闭合，抬升后积木是否随夹爪移动。
4. 只有单布局至少能稳定拿起积木后，再跑 `eval_num: native`，统计 15 分率、100 分率和平均分。
5. DP 离线训练通过后，再启动 DPPO；DPPO 的前缀 log-prob 修复仍保留。不要先跑长周期在线 PPO 来弥补离线基座的零成功率。

## 尚未能保证的事项

本修复没有 HDF5 数据、Isaac/PhysX 容器、GPU 与完整评测运行时，因此不能声称已在真实环境验证 90% 的 15 分率或 15% 的 100 分率。它解决的是代码中可确认的空间定位信息瓶颈、ACT latent collapse 风险、空间增强标签不一致和长开环执行问题；最终数值必须以服务器真实评测为准。
